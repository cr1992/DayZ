## 1. 产品定位与核心需求

做一款 **本地优先（local-first）、注重隐私、体验精致** 的跨平台日记应用，对标 Day One。

核心需求：

- **跨平台**：优先 iOS / Android，桌面端为远期可选。
- **富文本编辑**：图文混排、拖拽插入图片、丰富样式（标题/列表/引用/代码/待办等）。
- **时间线**：无限下拉/上滑，几千上万条带图日记流畅预览，按年-月分组、吸顶。
- **往年今日**：快速回顾历史上同一天（月-日匹配）的记录，可做成每日推送回访。
- **备份与导出**：区分”机器用的无损备份”与”给人看的可读归档”；备份支持全量/增量；数据可完整带走。
- **隐私加密**：本机数据与备份均加密，体现日记产品的信任承诺。
- **远期能力（预留，暂不实现）**：多端同步、全文搜索。

设计原则：**本地优先 + 数据可完整带走 + 默认加密**。同步在架构上预留字段不实现；加密则在本版纳入，因其与备份/还原深度耦合，事后追加代价大。

## 3. 数据存储层（定稿）

### 3.1 选型结论与理由

主库 **Drift**（SQLite 之上的类型安全 ORM），不选 NoSQL（Isar/ObjectBox/Hive）的原因：

- **招牌功能全是关系型查询**：游标分页、`month/day` 匹配往年今日、标签多对多 join、按条件筛选导出——SQL 的主场，NoSQL 要绕。
- **稳定性压倒性能**：日记是低频写入，不需要 NoSQL 的高吞吐；而 Isar/Hive 曾被原作者搁置转社区维护，存放用户多年人生的 App 不宜押注维护状态不明的库。ObjectBox 性能最强但非完全开源、不支持 Web，定位偏 IoT/POS 高频写入，与需求错位。
- **生态与演进**：Drift 文档完善、内置 migration 机制；远期 PowerSync 可与 Drift 配合做离线同步，为同步留好平滑路径，届时无需换库。

**关于”写 SQL 复杂”的澄清**：Drift 提供 Dart 风格查询 API（`select/where/orderBy/limit` 方法链，编译期检查 + 自动补全），90% 查询无需手写 SQL；表结构也用 Dart 类定义。本方案中的 `CREATE TABLE` 仅用于表达设计意图，实际由 Drift 生成。落地时所有数据库操作集中封装在 Repository 层，页面代码只调用如 `repo.onThisDay(5, 23)` 这样的方法，看不到查询细节。

### 3.2 三层存储职责

- **日记本体**（条目、媒体元数据、标签、关系、搜索）→ **Drift / SQLite（SQLCipher 加密）**
- **敏感小数据**（本机数据库密钥、备份相关口令）→ **flutter_secure_storage**（钥匙串/Keystore）
- **普通设置**（主题、排序、上次打开的笔记本）→ **shared_preferences**

> 关于 MMKV：它是高性能键值存储，等同”强化版 shared_preferences”，**没有查询能力，不能替代数据库**。仅可用于设置存储层，但日记本体场景下 shared_preferences 已足够，无引入必要。

## 4. 富文本编辑器选型（待定）

Flutter 自接管渲染、无 DOM/`contenteditable`，图文混排与图片拖拽缩放需”重写排版引擎”级工作量。以下方案并列，**建议一两天预研后再定**。

### 方案 A：纯 Flutter — AppFlowy Editor

- 开源 Notion 替代品抽出的独立编辑器包，纯 Dart，块编辑器，文档序列化为 JSON。
- **优点**：纯 Dart，无 WebView/JS 桥/接缝感，包体积小，调试一套语言，维护心智低。
- **风险**：图片细腻交互（相册拖入、拖拽缩放、图文环绕）是纯 Flutter 历史弱项，**能力上限需实测**；API 仍在演进；自家 JSON 格式，导出需自写转换器。

### 方案 B：WebView + TipTap（基于 ProseMirror）

- Flutter 内嵌 `webview_flutter` 加载本地打包的 HTML 编辑器（离线可用），JS 桥双向通信，存 `getJSON()`。
- **优点**：图片拖拽/缩放/图文混排为浏览器原生能力，开箱即用；体验天花板高；社区实践成熟。
- **风险**：JS 桥与原生-Web 接缝需打磨（WebView 高度/键盘自适应、首次加载白屏）；包体积增大；JSON 契约需两端一致。
- **体验优化**：插入图片不走 Web `<input type=file>`，改由 **Flutter 调原生相册/相机** 选图，存本地后路径回传 WebView 渲染。

### 备选（优先级低）

- flutter_quill（Delta，基础够用，混排/拖拽较弱）、super_editor（模型强、偏重）；Web 侧 Lexical、Editor.js。

### 选型对比

|维度           |A. AppFlowy Editor         |B. WebView+TipTap                         |flutter_quill|
|-------------|---------------------------|------------------------------------------|-------------|
|技术栈          |纯 Dart                     |Dart + Web/JS                             |纯 Dart       |
|图文混排         |支持                         |强                                         |较弱           |
|拖拽/缩放图片      |需实测（偏弱）                    |强（浏览器原生）                                  |弱            |
|接缝/桥接成本      |无                          |有                                         |无            |
|包体积          |小                          |较大                                        |小            |
|维护心智         |低                          |中                                         |低            |
|文档格式         |自家 JSON                    |TipTap JSON                               |Delta        |
|**PDF 导出路径** |JSON→HTML 或 widget→PDF（需另建）|**天然 HTML→PDF**（复用渲染）                     |需另建          |
|**远期同步/CRDT**|走 AppFlowy 自有 Rust 同步      |**ProseMirror + y-prosemirror 与 Yjs 原生咬合**|无现成 CRDT 路径  |


> **A/B 不只是”拖图顺不顺、中文跟不跟手”**：编辑器选型有三根触手伸进主干——① PDF 导出（8.5）依赖 HTML，只在 B 天然成立，A 手里没有 HTML，需 JSON→HTML 或 widget→PDF 另走一条；② `content_plain` 抽取器是编辑器专属，A/B 各写一套并与 `content_json` 保持同步；③ 远期 CRDT 路径被选型决定（见上表）。预研时应一并掂量长期的导出与同步代价，而非只看编辑手感。

### 预研验收标准

各搭最小 demo，测三件最影响日常体验的事：① 拖图进来顺不顺；② 图片能否缩放、混排是否自然；③ 中文输入法是否跟手。

**判定规则（明确化，避免拖盘）**：

- **图片交互（①②）是一票否决项**——它是日记最高频的日常体验，A 在此明显不足则后续”纯 Dart 长期收益”皆为空谈，**直接转 B**，不再纠结。
- 在图片交互过关的前提下，再以纯 Dart 长期收益（无桥接、包体积、维护）与上表的导出/同步代价综合权衡 A/B。
- **设硬性时间盒**（建议 ≤ 1 周）：到期必须出选型结论，不得无限期挂着拖住整盘。期间主干按下方临时策略照常推进。

> 临时策略：编辑器可先用简易版/纯文本占位，先把时间线、数据库、往年今日主干跑起来，后续替换，不阻塞主流程。

## 5. 数据库 Schema（定稿）

原则：**按”将来一定要做同步和加密”设计，但只预留字段不实现同步。**

关键决策：

- **主键 TEXT UUID（推荐 UUID v7，时间有序、索引友好）**，避免多设备冲突，且为备份还原提供去重判断依据。
- **区分”日记发生时刻”与”行创建时刻”**：`entry_dt_utc`（可编辑/回填）≠ `created_at`（不可变）。**回填/编辑 `entry_dt_utc` 或 `entry_tz` 时，`local_year/month/day` 三个冗余字段必须同步重算**（不只是首次写入时算好，编辑路径别漏，否则往年今日/分组会错位）。
- **时区三件套**：UTC 瞬间 + IANA 时区 + 本地年月日拆字段冗余（写入算好，查询命中索引）。
- **内容存两份**：`content_json`（编辑器 JSON）+ `content_plain`（纯文本，供搜索/预览/标题）。
- **媒体存文件系统**，库内只存相对路径 + 宽高。
- **全部软删除**（`deleted_at`）：既是同步墓碑，也是**增量备份能捕获”删除”的前提**。

```sql
CREATE TABLE journals (
  id          TEXT PRIMARY KEY NOT NULL,
  name        TEXT NOT NULL,
  color       TEXT,
  sort_order  INTEGER NOT NULL DEFAULT 0,
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);

CREATE TABLE entries (
  id            TEXT PRIMARY KEY NOT NULL,      -- UUID v7
  journal_id    TEXT REFERENCES journals(id),
  content_json  TEXT NOT NULL DEFAULT '',       -- 编辑器文档 JSON
  content_plain TEXT NOT NULL DEFAULT '',       -- 抽取的纯文本

  entry_dt_utc  INTEGER NOT NULL,               -- epoch 毫秒, UTC, 排序/同步
  entry_tz      TEXT    NOT NULL,               -- IANA, 如 'Asia/Shanghai'
  local_year    INTEGER NOT NULL,
  local_month   INTEGER NOT NULL,               -- 1-12  ┐ 往年今日/分组
  local_day     INTEGER NOT NULL,               -- 1-31  ┘ 写入时算好

  lat           REAL,
  lng           REAL,
  place_name    TEXT,
  weather_code  TEXT,
  weather_temp  REAL,

  is_favorite   INTEGER NOT NULL DEFAULT 0,

  created_at    INTEGER NOT NULL,               -- 行创建, 不可变
  updated_at    INTEGER NOT NULL,               -- 最近一次本地编辑（增量备份水位线依据）
  deleted_at    INTEGER,                        -- NULL = 存活（软删除墓碑）
  sync_status   INTEGER NOT NULL DEFAULT 0,
  server_rev    TEXT
);

CREATE TABLE media (
  id          TEXT PRIMARY KEY NOT NULL,        -- 被文档 JSON 引用
  entry_id    TEXT NOT NULL REFERENCES entries(id) ON DELETE CASCADE,
  kind        TEXT NOT NULL,                    -- image/audio/video
  rel_path    TEXT NOT NULL,                    -- 原文件相对路径（密文，设备密钥）
  mime        TEXT,
  width       INTEGER,                          -- 原图宽高，占位防滚动跳动
  height      INTEGER,
  duration_ms INTEGER,
  file_size   INTEGER,

  -- 缩略图缓存层（派生数据，不进备份，见 9.4）
  thumb_path  TEXT,                             -- 缩略图相对路径（密文）；NULL=未生成
  thumb_w     INTEGER,
  thumb_h     INTEGER,
  thumb_src_updated_at INTEGER,                 -- 生成缩略图时所依据的原图 updated_at
                                                -- 与原图当前 updated_at 不一致 = 缩略图过期需重建

  updated_at  INTEGER NOT NULL,                 -- 原文件最近变更（缩略图失效判断依据）
  created_at  INTEGER NOT NULL,
  deleted_at  INTEGER
);

CREATE TABLE tags (
  id TEXT PRIMARY KEY NOT NULL, name TEXT NOT NULL,
  created_at INTEGER NOT NULL, deleted_at INTEGER
);
CREATE TABLE entry_tags (
  entry_id TEXT NOT NULL REFERENCES entries(id) ON DELETE CASCADE,
  tag_id   TEXT NOT NULL REFERENCES tags(id)    ON DELETE CASCADE,
  PRIMARY KEY (entry_id, tag_id)
);

CREATE INDEX idx_entries_timeline ON entries(entry_dt_utc DESC) WHERE deleted_at IS NULL;
CREATE INDEX idx_entries_monthday ON entries(local_month, local_day) WHERE deleted_at IS NULL;
CREATE INDEX idx_entries_updated  ON entries(updated_at);          -- 增量备份用
CREATE INDEX idx_entries_sync     ON entries(sync_status);
CREATE INDEX idx_media_entry      ON media(entry_id);
CREATE INDEX idx_entrytags_tag    ON entry_tags(tag_id);

CREATE VIRTUAL TABLE entries_fts USING fts5(content_plain);       -- 本地, 永不上传
-- ⚠️ 默认 tokenizer 对中文几乎不可用（"上海"搜不出"在上海吃饭"）；
--    真做搜索时须改用 ICU 或 trigram tokenizer，详见第 11 节。

-- 编辑现场（自动保存暂存 + 崩溃恢复依据，见 7.3）
-- 【单行模型·定稿】固定单行（同一时刻只允许一个编辑现场）。多草稿并行列为非目标。
CREATE TABLE editing_session (
  id          TEXT PRIMARY KEY NOT NULL,        -- 固定常量主键（如 'current'），全表至多一行
  target_id   TEXT,                             -- 正在编辑的 entry id；NULL = 新建中
  draft_json  TEXT,                             -- 未提交的文档 JSON
  cursor_pos  INTEGER,                          -- 光标位置（可选）
  is_new      INTEGER NOT NULL DEFAULT 0,       -- 是否新建中
  updated_at  INTEGER NOT NULL
);
-- 残留行 = 上次异常退出；正常保存退出时清空本表
-- 切换编辑目标前必须先完成当前保存（覆盖该单行），不保留多份并行草稿
```

### 招牌功能查询验证

```sql
-- 时间线游标分页（(时刻,id) 元组游标，避免同时刻漏/重）
SELECT * FROM entries
WHERE deleted_at IS NULL AND (entry_dt_utc, id) < (?, ?)
ORDER BY entry_dt_utc DESC, id DESC LIMIT 30;

-- 往年今日
SELECT * FROM entries
WHERE deleted_at IS NULL AND local_month = ? AND local_day = ?
ORDER BY local_year DESC;
```

### 实战避坑

- **媒体存相对路径，不存绝对路径**：iOS 沙盒容器 UUID 重装/恢复后会变，绝对路径会全部失效致”图片集体丢失”。运行时用”当前媒体目录 + rel_path”拼接。
- **`entries_fts` 只存本地、不参与备份/同步**：天然兼容加密——上传/备份的是密文，本机解密后维护明文索引。
- 不把图片塞进 SQLite blob；标题取 `content_plain` 第一行。

## 6. 文档 JSON 契约（待与编辑器选型一并定稿）

文档序列化为 JSON 存入 `content_json`，需在 **Flutter 只读渲染器** 与 **编辑器** 间约定同一套结构，核心两条：

1. **图片节点引用 `media.id` 而非写死路径**——路径变化不影响文档完整性。
1. **预留自定义节点**：「位置块」「天气块」，导出时降级为文本行（`📍 上海` / `🌤 18°C`）。

> 字段结构待编辑器选型确定后补充（A 与 B 节点格式不同）。

## 7. 核心功能实现要点

### 7.1 时间线（无限滚动）

- **列表虚拟化**：`ListView.builder` / `Slivers`，仅渲染视口内项。
- **游标分页**：按 `(entry_dt_utc, id)` 倒序，每次 20~50 条。
- **分组吸顶**：`SliverList` + `SliverPersistentHeader`，年-月分组与吸顶 header。
- **防滚动跳动**：带图卡片按数据库记录的图片宽高先占位（解决”占多大”）。
- **图从哪来、解多快（关键）**：时间线**只读加密缩略图**（几十 KB 级，解密+解码快），绝不在滚动中解全尺寸原图（全尺寸只在打开单条时解）。缩略图未就绪时显示**纯占位**（灰块/blurhash），**不临时解原图降级**。缩略图缓存层的生成/加密/失效/节流见 9.4。占位仅解决”占多大”，缩略图缓存才解决”图从哪来、解多快”，二者缺一仍会卡。
- **通用化**：时间线设计为「接受查询条件 + 游标分页」的通用列表，使往年今日、标签、地点、搜索结果复用同一套 UI 与虚拟滚动逻辑（导出筛选亦复用此条件）。

### 7.2 往年今日

- 靠 `local_month` / `local_day` 索引匹配，按 `local_year DESC` 回看。
- **务必存本地日历日期**：用户记得的是”那天”，仅存 UTC 会因时区换算串到相邻日。
- 入口即”被过滤的时间线”（复用 7.1）。
- 可做 **每日定时本地通知**（“N 年前的今天…”）促回访。

### 7.3 自动保存与草稿恢复

核心思路：**自动保存是手段，草稿恢复是它的免费副产品**。每次保存都落进”编辑现场”记录，启动时发现该记录残留即说明上次异常退出。一张表 + 一个生命周期钩子即可，无需额外的崩溃检测机制。

**数据落地（两份分开）**

- 已成形内容 → 正式表 `entries.content_json`（防抖触发写入）。
- 未提交的编辑现场 → 独立的 `editing_session` 表（在编辑哪条、未提交 JSON、是否新建、光标）。**单行模型**：全表至多一行，同一时刻只有一个编辑现场；**切换编辑目标（如从 A 日记跳去编辑 B）前必须先完成当前保存**，覆盖该行，不保留并行草稿。多草稿并行为非目标。
- 正常保存退出时**清空 `editing_session`**；**该表有无残留行 = 上次是否异常退出的唯一判据。**

**保存触发（两个，主 + 命）**

- **输入停顿 1.5 秒** → 防抖保存（主力，覆盖正常书写；非逐字符、非固定间隔）。
- **App 切后台 `AppLifecycleState.paused/inactive`** → 立刻强制保存（保命，覆盖”被杀”；系统杀后台前几乎都先回调 paused）。
- 退出编辑页归入正常保存流程。其它触发器先不做。

**恢复体验（默认温和，可配置）**

- 启动停在时间线；若检测到残留草稿，**顶部非阻断提示条**：“有一篇未保存的草稿 · 继续编辑 / 丢弃”。
- 设置项”恢复未完成的编辑”（默认**开**）。“启动直接进入编辑页”作为该设置下的**可选激进子项**，不作默认（避免绑架导航）。

**WebView 方案（B）必做项**

- `paused` 时向 WebView 异步取 `getJSON()` 可能在系统冻结前来不及。故 **TipTap 每次内容变化即主动经桥推送最新 JSON 至 Flutter 内存缓存**；paused 时 Flutter 直接同步写盘，不依赖那一刻的异步往返。纯 Flutter 方案（A）内容本在 Dart 侧，无此问题。

**保命细节**

- 写盘**原子化**（事务或临时文件替换），草稿永远是完整可解析 JSON。
- 自动保存失败**静默重试**，绝不弹窗打断书写。
- 内容无变化用脏标记**跳过保存**，省 I/O 与电。
- 草稿同处 SQLCipher 加密库内，未提交隐私内容一并受保护（被加密方案自动覆盖）。

**给 AI 的需求（框定）**

> 自动保存采用双触发：输入防抖 1.5s + `AppLifecycleState.paused/inactive` 强制保存，退出编辑页保存。正式内容写 `entries.content_json`；同时维护 `editing_session` 记录编辑现场（target_id、draft_json、is_new、cursor_pos）。WebView 方案下编辑器内容变化即经桥推送最新 JSON 至 Flutter 内存缓存。启动检测到残留 `editing_session` 即判定上次异常退出，按设置项（默认开）以非阻断提示条引导恢复，可选直接进编辑页。写盘原子化、失败静默重试、无变化跳过。

### 7.4 撤销与重做

核心建议：**不自行实现撤销栈，直接复用编辑器内置 history。** 富文本撤销的真正难点在”操作合并粒度 + 光标恢复 + 输入法边界”，这些 ProseMirror（TipTap 底层）与 AppFlowy Editor 已打磨成熟；自行重写只会引入 bug。开发只负责把 UI 按钮/快捷键接到编辑器命令。

- **实现方式**：TipTap history 扩展（`editor.commands.undo()/redo()`）或 AppFlowy undo manager，直接使用。
- **与自动保存的边界**：撤销针对**编辑操作**，自动保存是后台静默写盘，**不得进入 history**。用编辑器自带 history 时天然成立——history 只记文档变更，与写盘时机无关。
- **与草稿恢复的边界**：App 被杀后从草稿恢复，**撤销历史会丢失**（history 是内存态）。**不持久化 history**（成本高、易错，且用户无强预期）；恢复后内容在、撤销栈从恢复点重新开始。此为行业惯例。
- **撤销范围**：仅**正文编辑**纳入。标题、标签、日期等结构化字段**不纳入**富文本撤销栈（各自简单状态，单独处理或不做），否则撤销行为不可预测。
- **历史深度**：用编辑器默认值，不必调。
- **快捷键**：移动端 MVP 主要靠工具栏按钮；将来上桌面/外接键盘再接 `Cmd/Ctrl+Z`、`Cmd/Ctrl+Shift+Z`。
- **WebView 方案（B）衔接**：撤销/重做按钮置于 **Flutter 工具栏**（体验统一），点击经桥调用编辑器命令；同时编辑器须经桥同步 `can().undo()/redo()` 状态，以正确控制按钮置灰（否则按钮永远高亮、点了无反应）。纯 Flutter 方案（A）直接调 undo manager，无此桥接。

**给 AI 的需求（框定）**

> 撤销/重做复用编辑器内置 history（TipTap history / AppFlowy undo manager），不自行实现。仅正文纳入撤销范围，结构化字段不纳入。自动保存为静默写盘，不影响 history。草稿恢复后 history 从恢复点重启（不持久化）。WebView 方案：按钮置于 Flutter 工具栏经桥调命令，编辑器经桥同步 can().undo()/redo() 控制按钮可用态。

## 8. 备份架构（定稿）

### 8.1 两类导出，目标不同，分开设计

|用途         |主格式                 |辅格式 |目标            |
|-----------|--------------------|----|--------------|
|**备份（给机器）**|**加密备份包**（见 8.2/8.3）|JSON|无损、可还原、高性能导入  |
|**归档（给人看）**|**PDF**             |HTML|排版漂亮、成品感、可打印珍藏|

### 8.2 备份包格式与后缀

备份产物有**两种形态**，对应不同阶段，二者格式一致、区别仅在”是否存在一个持久、可重复读取的备份位置”：

**形态一 · 单文件快照（MVP）**

- 一次性导出**单一文件**，用**自定义后缀**（如 `.mydiary`），而非 `.db`：隐藏实现细节、防误操作，并可在 iOS/Android 注册文件类型关联，实现”双击/分享即唤起 App 还原”的闭环。
- 本质为容器，内含 **数据库文件 + `media/` 目录 + `manifest`（含 `schema_version`、备份类型、生成时间等）**，加密后为二进制（见第 9 节）。
- **自包含、独立可还原**，用户存到哪都行（本地、手动上传网盘、AirDrop）。MVP 即此形态。

**形态二 · 持久备份目标（阶段二）**

- 一个**长期存在、App 可重复读取**的备份位置（如固定备份文件夹、iCloud/某网盘目录），App 能在其中持续累积、并重新读取既有内容以计算差集。
- **media 增量（8.3）依赖此形态**——单文件快照里没有”目标侧”可供比对，增量无从谈起。
- 排在 MVP 之后，需先确立”持久备份目标”这一概念与具体落地（目标位置如何选择、授权、持久化句柄）。

### 8.3 全量 / 增量设计

> 注意：此处增量指**单向备份**，非多端同步，不涉及冲突合并。其前提（`updated_at` + `deleted_at` 墓碑 + UUID）schema 已具备。
> 
> **⚠️ 阶段边界（v0.6 修正）**：全量可独立成立于”单文件快照”（形态一，MVP）；**media 增量必须依附”持久备份目标”（形态二，阶段二）**。MVP 不实现 media 增量——单文件快照中不存在可比对的”目标侧”，强行实现会迫使 AI 自造本地清单，正好踩中下文明令禁止的 desync 坑。

**全量备份（Full）—— MVP 即做**

- 定位：自包含完整快照，独立可还原；落地为形态一单文件。
- 导出：`VACUUM INTO 'full_<ts>.db'` 生成干净紧凑副本（正确处理 WAL，避免写一半的脏状态）+ 全部 media，打包加密为 `.mydiary`。
- 还原：整库覆盖（换 db 文件 + media 拷回），瞬间到位。
- 特点：体积大，但还原最快最可靠、无依赖。**MVP 的备份就是它。**

**media 增量（Incremental）—— 阶段二，依赖持久备份目标**

- 定位：每次只向持久备份目标补传”上次之后新增/变化的媒体”，db 仍每次全量覆盖（见下推荐方案）。
- **前置条件**：已确立形态二的持久备份目标。否则本节不成立。
- **“已备份清单”的唯一真相来源 = 备份目标侧**，不存本地。理由：清单存本地会与实际备份目录 desync（用户删了某个备份文件，本地仍以为已传，该图永久缺失）。每次增量前以**备份目标实际存在的媒体**为准计算差集。
- **孤儿媒体清理**：db 每次全量、删除靠 db 捕获，但备份目标里不再被任何 entry 引用的旧媒体会累积成孤儿（无害但占空间）。提供低频”备份瘦身”：比对最新全量 db 实际引用的 `media.id` 集合，清除目标侧孤儿（谨慎、可选、有确认）。

**推荐落地方案（性价比最优，阶段二）：库全量 + media 增量**

> 日记数据特征是”数据库小、媒体大”。故在持久备份目标上：**数据库每次全量**（`.db` 小，`VACUUM INTO` 毫秒级、可独立还原、无链条复杂度）+ **media 增量**（对比目标侧已存在媒体，只补新增图）。
> 这样拿到增量 90% 的收益（省掉重复拷贝大量老照片），又完全避开”条目级增量链条”的断链风险（db 始终完整、无需叠加）。仅当库将来极大（数据库本身上百 MB）时，再考虑完整的条目级增量。

> **关于”完整条目级增量”**：即 db 也只导出 `updated_at > 水位线` 的变化条目、还原需”全量基底 + 顺序叠加”。它链条复杂、有断链风险（缺一包则后续不可用），本方案**不采用**，仅作为库极大时的远期备选记录在此。

三种方案对照：

|    |纯全量（MVP）|完整条目级增量（不采用）|**库全量+media增量（阶段二推荐）**|
|----|--------|------------|----------------------|
|备份目标|单文件快照即可 |需持久目标       |需持久目标                 |
|数据库 |全量      |增量条目        |全量（小，毫秒级）             |
|媒体  |全量      |增量          |增量（只补新图）              |
|独立还原|✅       |❌ 需基底+叠加    |✅（db 始终完整）            |
|断链风险|无       |有           |无                     |
|体积  |大       |最小          |小                     |
|复杂度 |低       |高           |低                     |

### 8.4 还原逻辑

**整库覆盖式还原（对应全量 / 推荐方案）**

1. 校验 `schema_version` 兼容性（不一致则走 App 升级 migration，或拒绝并提示）。
1. 解密备份包，取出 db 文件与 media。
1. 关闭当前数据库连接 → 用备份 db **替换**当前 db 文件 → media 拷入**当前设备**媒体目录（保持相对路径）→ 重启数据层。
1. **重建 `entries_fts` 索引**（派生数据不在备份内，必须重建，否则”日记都在但搜不到”）。FTS 重建是纯 CPU、秒级，可同步完成。
1. **缩略图：懒生成 + 后台预热，绝不在还原时同步全量重建**。缩略图同为不进备份的派生数据，但其重建是”解码原图→降采样→重编码→加密落盘”的重活，几千张为分钟级。若还原时同步全量重建，会把”换文件瞬间到位”的爽快彻底抵消，卡死在还原步骤。正确做法：还原后**立即可用**（时间线滚到哪、缩略图生成到哪，未就绪时显示**纯占位**——灰块/blurhash，**绝不在滚动中临时解全尺寸原图**，详见 7.1/9.4 口径），同时**后台 isolate 低优先级**逐步补齐全量缩略图。

> ⚠️ 给 AI 的明确约束：此处**不得**实现为”还原时同步全量重建缩略图”。
1. **整库覆盖前必须二次确认**（高危，会覆盖现有数据）。

**合并式还原（对应 JSON 备份，可选性恢复）**

- 在单个数据库事务内，按 UUID 做 **合并/覆盖/跳过**（默认合并：库无则插入，已存在按 `updated_at` 决定是否覆盖；有 `deleted_at` 则删除）。
- media 拷入当前目录并保持相对路径；完成后重建 FTS；缩略图同样懒生成 + 后台预热；任一步失败整体回滚。

**给 AI 的还原需求（一句话框定）**

> 读取备份包，校验 `schema_version`；整库覆盖式：关闭连接后替换 db 文件、media 拷回当前目录、重启数据层、重建 FTS（同步）；缩略图懒生成 + 后台 isolate 预热（**禁止还原时同步全量重建**）；合并式：单事务内按 UUID upsert + 墓碑处理。任一失败整体回滚并提示；覆盖式还原前二次确认。

### 8.5 给人看的归档（PDF / HTML）

- **PDF（主）**：一年/一段一本，带封面、目录、页眉日期、图文混排。实现用 **HTML→PDF**。

> ⚠️ **此路径因编辑器选型而异**：方案 B（WebView+TipTap）天然有 HTML，“复用文档渲染能力”成立；**方案 A（AppFlowy）手里没有 HTML**，需先将 AppFlowy JSON 转 HTML，或改走 Flutter widget→PDF 另一条路。PDF 导出的实现成本是 4 节 A/B 权衡的一部分。
- **HTML（辅）**：自包含单文件（图片内嵌 base64 或同级文件夹），双击即看、体积小。
- **可读性细节**：日期一律**本地日期**（`2026-05-23 周五`）非 UTC；标题取 `content_plain` 第一行；自定义块人话化（`📍`/`🌤`）；按时间**正序**排（归档从过去读到现在）。

### 8.6 批量导出工程要点

- **后台 isolate 执行**，不占 UI 线程，避免大库卡死。
- **流式写入**，逐条处理写盘/写包，避免几 GB 媒体一次性入内存 OOM。
- **进度反馈**：进度条、可取消、可断点。
- **媒体去重**：同图被多条引用按 `media.id` 只打包一份。
- **筛选导出**：复用「查询条件」设计，支持按笔记本/时间范围/标签。

## 9. 加密方案（定稿：SQLCipher + 混合密钥，加密可选）

### 9.1 选型结论

采用 **SQLCipher（加密版 SQLite）**，数据库文件**始终为密文**，本机与备份一套密钥体系到底。理由：

- **与”换文件”高性能还原咬合**：db 本身即密文，备份直接拷密文、还原直接换密文文件，**导出零额外加密步骤**，高性能路线原样保留，且无明文落临时文件的泄露窗口。

> 注意：此”无明文落临时文件”仅对 **db** 成立。**媒体**走”设备密钥解密 → 备份口令重加密”的中转，必须保证明文只在内存/流中、**不落临时文件**（尤其大视频别图省事 temp 一下），与流式导出（8.6）一起执行。
- **本机数据同样安全**：手机丢失/取证也无法读取，符合日记产品信任承诺。
- **与远期 E2E 同源**：密钥派生（Argon2id）是共用地基，将来同步加密直接复用。
- **接入低侵入**：Drift 经 `sqlcipher_flutter_libs` 接入，上层 Dart 查询代码几乎无感。

### 9.2 混合密钥策略（关键）

- **本机日常**：设备生成**随机密钥**，存系统钥匙串/Keystore（iOS Secure Enclave / Android Keystore 硬件级保护）。用户**无感**，App 启动自动解锁，零摩擦。
- **备份**：导出时用**用户备份口令经 Argon2id 派生的密钥**对备份包**重新加密**。保证**换机/跨设备可恢复**（口令在用户记忆中，不绑设备）。备份为低频操作，重加密开销可接受。

> 这样解决了备份加密最经典的致命坑——若密钥只在原设备，换机后备份成”打不开的密文砖头”。备份口令使其可在任意新设备重建密钥。

### 9.3 密钥派生模块（共用底座）

- 独立模块：**用户口令 → Argon2id → 密钥**。
- 首个使用方是备份加密；远期 E2E 同步复用，不重写。

### 9.4 媒体加密与缩略图缓存层

这是性能与加密**两头都踩**的一块，必须显式设计——否则 7.1 的”防滚动跳动”只解决了占位，没解决”图从哪来、解多快”。

**为何不能只靠原图加密**：核心需求是”几千上万条带图日记流畅预览”。若时间线每显示一张就解密 + 解码一张全尺寸原图，必然卡顿。需要一套缩略图缓存层。

**缩略图缓存层设计**：

- **生成**：媒体入库时生成降采样缩略图（如长边 ≤ 数百 px），单独存储，登记进 media 表（`thumb_path` / `thumb_w` / `thumb_h`）。
- **加密**：缩略图**同样加密**——它也是隐私内容，泄露缩略图等于泄露画面。与原图一致用**设备随机密钥**（见下”密钥归属”）。
- **读取分层**：时间线滚动**只解密+解码缩略图**（几十 KB 级，快）；全尺寸原图**仅在打开单条日记时**解密。
- **未就绪显示口径（统一，重要）**：缩略图尚未生成好时，卡片显示**纯占位**（灰块或 blurhash），**绝不在滚动中临时解全尺寸原图降级**——“滚动中解原图”正是 7.1 极力避免的卡顿源，二者口径必须一致。
- **滚动节流（防猛滑抖动）**：快速滑动时视口数百毫秒掠过几十条，若每条都触发”解码→降采样→加密落盘”会瞬间排起一长串多为滑过即弃的重活。故缩略图生成采用：**滚动停下再触发**，或**可取消任务队列**（视口移走即丢弃该任务）。后台预热任务亦为低优先级、可被前台滚动需求抢占。
- **不进备份**：缩略图是**可重建的派生数据**（同 FTS 索引），不打包进备份，省体积。还原后按原图重建，但**还原期必须懒生成 + 后台预热，不可同步全量重建**（详见 8.4 第 5 步）。
- **失效与重建（脏判断）**：换首图、原图被替换/编辑后，缩略图须失效重建。判断依据：**对比 `thumb_src_updated_at` 与原图当前 `updated_at`**，不一致即过期、触发重建（无需单独的脏标志位，靠时间戳比较天然不会漏置位）。

**密钥归属（明确决策）**：

- 原图与缩略图**始终用设备随机密钥**（Keystore/Secure Enclave），**不随应用主密码走、不参与 rekey**。
- 理由：若媒体跟主密码走，改密码就要重新加密可能数 GB 的图片/视频，体验灾难；设备密钥已是硬件级保护。
- **由此引出一个反直觉但必须向用户讲清的结论**（见 9.7 文案定调）：设了应用主密码，实际只为**正文文字**（`content_json`/`content_plain`）加了主密码这道锁；**全部视觉内容（原图 + 缩略图）的静态保护停在 Keystore 级**，不随主密码提升。

**媒体明文不落盘**：备份导出时媒体的”设备密钥解密 → 备份口令重加密”中转，明文只在内存/流中，不落临时文件（见 9.1 注、8.6）。

### 9.5 必须向用户讲清的代价（产品责任）

- **忘记备份口令 = 该备份永久无法恢复，无后门**（有后门即不安全）。UI 必须反复警示、引导妥善保存口令。
- SQLCipher 读写有轻微加解密开销，对日记低频访问**无感**。

### 9.6 跨设备导入流程

核心认知：**本机密钥与备份密钥是两把不同的钥匙**，这正是混合密钥设计能跨设备的原因。

- **本机随机密钥**：存 Keystore/Secure Enclave，硬件保护下**不可导出、锁死本设备**——这是安全特性。因此直接拷贝 A 设备的密文 db 到 B 设备**无法打开**（B 没有那把密钥）。
- **备份口令派生密钥**：从用户口令经 Argon2id 现算，**不绑设备**，任意设备凭同一口令可重建。

**导出（A 设备）**：本机随机密钥解密 → 内存中得明文（短暂）→ 备份口令派生密钥重新加密 → 备份包。

**导入（B 设备）**：

1. 用户打开备份包，**输入备份口令**。
1. B 用相同 Argon2id 算法从口令重建备份密钥（算法 + 口令一致 → 必得同一密钥）。
1. 解密备份包得明文数据。
1. B **生成自己的全新随机密钥**（存入 B 的 Keystore），用它把数据重新加密落地为 B 的本机库。

要点澄清：

- **跨设备导入需输入备份口令**——这是设计意图，口令是脱离设备的”数据通行证”，不是缺陷。
- **口令只在导入那一刻用一次**；导入后 B 与 A 一样无感解锁，日常不再需要口令。
- 每台设备各有本机密钥，但**共认同一备份口令**，口令即设备间流转的桥梁。
- 设备间直接传输（不经备份包）属”同步”范畴（第 11 节，远期）；当前一律走”备份包 + 口令”。

### 9.7 可选加密：模式矩阵与状态切换

加密对用户**可选**：兼顾”怕忘密码丢数据”的多数人与”要更强安全”的高敏感用户。但底层须拆成**两个独立维度**——本机密钥模式、备份口令——而非单一开关。

**本机始终经 SQLCipher 加密**（开销无感，无理由关闭，保证手机丢失/取证亦安全）。可选的只是**密钥怎么管**：

|本机模式       |本机库         |密钥来源            |用户感知    |适合      |
|-----------|------------|----------------|--------|--------|
|**无密码（默认）**|SQLCipher 加密|设备随机密钥（Keystore）|无感，自动解锁 |多数人，怕忘密码|
|**设应用密码**  |SQLCipher 加密|主密码 Argon2id 派生 |启动/隔段输密码|高敏感用户   |

**备份口令不可”裸奔”**：本机可无密码，但备份动作必须保证产物既不明文外流、也不锁死设备。组合约束：

|本机  |备份        |是否允许                                         |
|----|----------|---------------------------------------------|
|无密码 |无加密       |⚠️ 仅引导导出至本机私有目录，App 内**隐藏分享/上传入口**（见下”无法技术强制”）|
|无密码 |设备密钥加密    |❌ 禁止（换机打不开）                                  |
|无密码 |**备份口令加密**|✅ 推荐——本机无感，备份时单独设口令                          |
|有主密码|复用主密码     |✅ 最省心，一密到底                                   |


> **“禁止外传”无法技术强制**：文件一旦落进用户可见目录，OS 层面拦不住分享/上传。所以这只能是 **App 内的 UX 护栏**（隐藏分享按钮 + 强提示），措辞上**不可向用户承诺”绝对拦得住”**。真要安全外传，引导用户选”备份口令加密”。

**交互建议**：

- 本机：默认”无密码（已启用设备加密保护）”，设置中可选”设置应用密码”增强。
- 备份导出：有主密码→提示复用或另设独立口令；无主密码→**强制为本次备份设口令**，并告知”无口令备份不能跨设备恢复、不应上传云端”。

**「主密码不保护照片」的用户文案定调（重要，反直觉，必须主动解释）**：

- 事实（来自 9.4 密钥归属）：原图与缩略图始终用设备密钥、不随主密码走。故**设了应用主密码，实际只为正文文字加锁，全部视觉内容的静态保护停在 Keystore 级**。
- 为何反直觉到需要解释：日记用户的直觉恰恰是”照片比文字更需要锁”（9.4 也写了”图片往往比文字更敏感”），结果主密码偏偏不锁照片——**不解释，用户会当成缺陷或安全漏洞**。
- 文案应主动定调，讲清两点：① 照片用的是**另一套同样硬件级**（Keystore/Secure Enclave）的保护，并非”没锁”；② 这样**反而更可靠**——不会因为忘了主密码连照片一起被锁死、永久打不开。
- 这条不属于”边角料技术说明”，应在**设置/隐私说明的 UI 文案**里单独、清楚地呈现。

**状态切换（换锁，必须事务安全）**：

- 无密码 ⇄ 设密码、改密码，均走 **SQLCipher rekey**（用旧密钥解密、新密钥重加密整库）。**仅 db rekey；媒体不重加密**（媒体始终设备密钥，见 9.4），避免改密码触发数 GB 媒体重加密。
- rekey 是重操作：**后台执行 + 进度提示 + 事务安全 + 失败回滚**，中途崩溃不得使库变成新旧密钥都打不开的砖头。

### 9.8 给 AI 的加密需求（框定）

> 本机数据库始终经 SQLCipher 加密。密钥管理可选两档：默认”设备随机密钥（Keystore/Secure Enclave，无感解锁）”，可选”用户主密码（Argon2id 派生）”。切换/修改密码走 SQLCipher **db rekey**（媒体不重加密），后台执行、进度提示、事务安全、失败回滚。
> 媒体（原图 + 缩略图）**始终用设备随机密钥**，不随主密码走、不参与 rekey。UI 须主动说明”主密码不保护照片，照片由设备级密钥保护，反而不会因忘密码被锁死”。
> 备份导出独立处理：用”备份口令 → Argon2id 派生密钥”对备份包（db + media + manifest）加密为自定义后缀文件；有主密码可复用，无主密码则**强制为该备份设独立口令**。“无加密且外传”只能用 UX 护栏（隐藏分享入口 + 强提示）引导，**不承诺技术强制拦截**。媒体明文中转不落临时文件。
> 跨设备导入：输入备份口令重建密钥解密，再以新设备自身随机密钥重新落地本机库；口令仅导入时用一次。
> 密钥派生（Argon2id）独立成模块，供备份与远期 E2E 复用。**移动端需实测调参**（内存代价过高低端机 OOM/卡顿、过低削弱安全），并预研期先验证选定 Dart Argon2 库的可用性与维护活跃度。所有口令丢失不可恢复，UI 明确反复警示。

## 10. 关于引入 Rust（结论：暂不需要，按需再上）

- 导出/备份瓶颈大概率在 **I/O**（读图、压缩、写盘），Rust 与 Dart 差距小；真正吃 CPU 的是**图片批量重编码 / 大批量 PDF 渲染**。
- **Dart isolate 已能解决卡 UI**，纯 Dart + isolate 对备份/导出体验完全可接受。
- Rust 代价：FFI 工具链、各平台交叉编译、CI 改造、跨语言调试、包体积、多养一门语言。
- **路径**：先纯 Dart + isolate 实现并测真实耗时；若某环节确为瓶颈（几乎只会是图片重编码或 PDF 渲染），**仅该环节**下放 Rust，边界干净（入字节、出字节）。
- **例外**：若规划用 Rust 写跨平台核心引擎（同步 / 加密 / CRDT，如 AppFlowy 后端即 Rust），则早搭 Rust 工具链值得，备份顺带受益——属更高层架构决策。

## 11. 远期能力（预留，暂不实现）

- **同步**：Supabase（最快验证）/ PowerSync / ElectricSQL（SQLite↔Postgres 双向）/ CRDT（Automerge、Yjs，富文本并发合并最佳但成本高）。富文本 JSON 并发冲突合并是难点，故预留 CRDT。**注意 CRDT 路径受编辑器选型决定**（TipTap/ProseMirror ↔ Yjs 原生咬合；AppFlowy 走自有 Rust 同步），见第 4 节对比表。
- **端到端加密**：复用第 9 节 Argon2id 派生模块，服务器只存密文。**Argon2id 移动端参数需实测调参**，并预研期先验证 Dart 侧库（多为 FFI 绑定）的维护活跃度。
- **全文搜索**：FTS 索引本地、明文、不上传，已天然兼容加密。**⚠️ 中文非轻活**：默认 fts5 tokenizer 对中文几乎不可用（“上海”搜不出”在上海吃饭”），须改用 **ICU 或 trigram tokenizer**——别当成”接个 FTS 就好”。

数据模型已预留：稳定 UUID、`created_at`/`updated_at`、软删除墓碑、`sync_status`、`server_rev`，确保后期加同步无需痛苦迁移。
