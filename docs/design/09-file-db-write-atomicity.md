# 09-文件与数据库写入原子性约定

> 适用范围：全项目所有「文件系统操作 + 数据库写入」需要保持一致的场景。
> 状态：定稿（v0.6）
> 引用方：`specs/active/thumbnail-cache`（R8）、`specs/active/backup-full-snapshot`（R5/R8）等。

## 1. 问题：文件 IO 进不了 SQLite 事务

SQLite/Drift 的事务只覆盖**数据库行**的原子性，**文件系统写入（写文件、rename、删文件）不在事务边界内**。因此「在同一个事务里同时改文件和数据库行、任一失败全回滚」在物理上不可实现——事务回滚不会撤销已经落盘的文件，文件操作失败也不会自动回滚已提交的行。

强行把这两件事写成「同一事务原子完成」是一条**伪原子性**需求，会逼迫实现者写出实际做不到、却假装做到的代码。本约定确立两套**可落地的补偿式次序**，替代不可能的「真原子」。

## 2. 约定一：通用写入（新增 / 更新派生文件）——先文件后 DB、DB 失败删文件

适用：缩略图生成、缓存文件落盘、单个媒体写入等「写一个新文件 + 在 db 记一笔」的场景。

**统一次序：**

1. **写文件到临时名** `<target>.tmp`（同目录，保证 rename 不跨文件系统）。
2. **rename** `<target>.tmp → <target>`（POSIX rename 对单文件原子）。
3. **DB 事务**更新指向该文件的字段（如 `thumb_path`）。
4. **若 DB 事务失败**：删除步骤 2 写好的文件，使「文件在、db 无引用」的孤儿不残留；调用方收到失败。
5. **若进程在第 3 步前崩溃**：留下的是孤儿文件（db 未引用），无害，由后续运维/启动清扫处理；db 一致。

**不变式：** db 中任何指向文件的字段，其文件必然已落盘；不会出现「db 说有、文件没有」的悬空引用。反向的「文件在、db 无引用」是可容忍的孤儿（占空间但不破坏一致性）。

**禁止：** 不得声称「在同一 db 事务内同时更新文件与表」。文件 IO 在事务外，按上述次序补偿即可。

## 3. 约定二：覆盖式还原（整库 + 大批文件一起替换）——写临时位置 + 全成功后原子切换 + 失败保留旧态

适用：备份还原这类「用一整套新的 db + 一整批新 media 覆盖现有的 db + media」的高危场景。这里约定一不够用——因为它要同时替换**多个**互相引用的产物（db 引用 media，media 必须与 db 匹配），任何中途失败都不能让旧 db 引用到已被破坏的 media。

**统一次序：**

1. **全部新产物先写到临时位置**，不触碰任何现役文件：
   - 新 db 写到 `<db>.restoring`；
   - 每个新 media 写到 `<media>/.restoring/<id>.bin`（独立临时目录），逐个流式解密+重加密落到这里。
2. **全部临时产物写成功后，才进入切换阶段**；切换阶段只做 rename（目录级或逐文件），尽量短、不可中断的步骤集中。
   - `<db>.restoring → <db>`；
   - `<media>/.restoring/ → <media>/`（先把旧 `<media>/` 移走或在切换成功后再删旧的，保证任一时刻要么全旧、要么全新）。
3. **任一步失败（写临时、解密、重加密、空间不足等）**：只删除临时产物（`.restoring` 文件 / 目录），**旧 db 与旧 media 原封不动、原样可用**。调用方收到失败，本机数据等价于「从未还原」。
4. 切换成功后，再清理被替换下来的旧产物。

**不变式（覆盖式还原后本机状态二选一）：**
- **要么全新**：新 db + 与之匹配的新 media 全部就位；
- **要么全旧**：旧 db + 旧 media 完整可用。

**绝不允许的中间态：** 先清空/删除现役 media、再写回、写到一半失败回滚到旧 db——这会造成「旧 db 在、但它引用的 media 已被清空」的数据丢失（db 在、图全丢）。**严禁先破坏现役产物再写新产物**；新产物必须先在临时位置就绪，旧产物在切换成功前一律不动。

## 4. 选哪一套

| 场景 | 用约定 | 关键差异 |
|------|--------|----------|
| 写一个派生文件 + 记一笔 db（缩略图、缓存） | 约定一 | 单文件，先文件后 db，db 失败删文件 |
| 覆盖式还原（整库 + 整批 media） | 约定二 | 多产物互相引用，全部写临时位置、全成功再原子切换、失败保留旧态 |

## 5. 与清理约定的关系

两套约定都会产生临时产物（`.tmp` / `.restoring`）。这些临时产物的清理（正常路径 finally 删、异常路径 finally 删、启动时扫残留）由各功能 spec 的「中间产物清理」需求承接（如 backup 的 NF5）。本文只规定**写入次序与失败时的旧态保全**，不重复定义清理细节。
