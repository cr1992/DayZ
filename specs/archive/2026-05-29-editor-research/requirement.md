# editor-research（编辑器 A/B 预研）

## 背景

v6 第 4 节明确编辑器是「唯一真正难点」，方案 A（AppFlowy Editor，纯 Dart）与方案 B（WebView + TipTap）并列待选。第 4.5 节定调先做最小 demo 实测三件事（拖图、缩放/混排、中文输入法），并设了一票否决（图片交互不足直接选 B）与硬性时间盒（≤1 周）。本里程碑只为出选型结论：跑两个最小 demo、把判定数据钉死、产出对后续 spec 的指令（编辑器集成 / JSON 契约 / PDF 导出走哪条路）。

## 范围外

- 编辑器**完整集成**到主 App 流（含工具栏、自动保存对接、文档 JSON 契约）——选型出结论后另立 spec。
- JSON 文档格式落定——同上。
- PDF / HTML 导出——同上。
- 撤销/重做接入——同上。
- 长期同步路径（CRDT）——远期。

## 需求

### R1 · A 方案最小 demo
系统 SHALL 在 Debug Home 注册「AppFlowy 编辑器 demo」入口；demo 内能做：① 输入文字；② 插入本地图片；③ 拖动/缩放图片；④ 回显内容（控制台或屏幕上）。
- 前提：M0 已就绪、Debug Home 可挂入口
- 操作：点入 demo
- 结果：完成上述四步可见、可重复

### R2 · B 方案最小 demo
系统 SHALL 在 Debug Home 注册「WebView+TipTap 编辑器 demo」入口；demo 内同样支持 ①②③④；WebView 内 HTML 离线打包（不联网）；图片插入路径走 **Flutter 调原生选图 → 路径回传 WebView 渲染**（不走 Web `<input type=file>`）。
- 前提：同上
- 操作：点入 demo
- 结果：四步可见、可重复，无 WebView 白屏卡 > 1s

### R3 · 评测三件事
> **归档说明（@Ray 2026-05-29 拍板）：本需求以决策替代、不再实测。** 经 @Ray 于 2026-05-29 直接拍板选定方案 A，下述正式三件事真机实测未进行、亦不补录；R3 不再作为「应实测却没实测」的悬空项。原始需求文本保留如下仅作存档。

对 A 与 B 分别评测：
- ① 拖图进来顺不顺（操作流畅度、错误率）
- ② 图片能否缩放、图文是否自然混排
- ③ 中文输入法是否跟手（拼音连续输入不丢字、不回车截断、IME 候选框不卡）

评测结果 MUST 以表格形式记入本 spec 的 `verification 段落或 tasks 验收记录`（含设备型号、平台、操作录屏链接或截图）。

### R4 · 一票否决与时间盒
- 若 A 在 ① 或 ② 任一项明显不足（操作明显卡顿、图无法缩放、混排错乱），SHALL **直接选 B**，不再纠结纯 Dart 长期收益（v6 4.5 定调）。
- 整个里程碑设硬性时间盒：**≤1 周必须出结论**。到期即使数据不全也必须拍板，由 @Ray 拍。

### R5 · 选型结论落档
结论 MUST 同步到三处：
1. 本 spec 的 verification 段或 tasks 末尾的「选型结论」记录块；
2. `specs/README.md` 顶部追加「编辑器选型 = A / B」一行（或在本里程碑归档时附带）；
3. `docs/design/03-rich-text-editor-research.md` 第 4 节末尾追加「v0.7 选型补丁：选定 X，理由 Y」（不改原文，仅追加）。

后续依赖该结论的 spec（编辑器集成、JSON 契约、PDF 导出、撤销/重做）才能开工。
